# Задания в базу данных — проект схемы

Дата: 2026-07-29. Статус: **на согласование, миграции не написаны.**

## Зачем

Сейчас источник истины — JSON в `storage/app/tasks/`. Пять банков, 8377 задач,
41 разный `type`. Переезд нужен по четырём причинам, и все они видны в коде.

**Половина переезда уже случилась.** В БД лежит всё, что меняется в рантайме:
`task_statuses`, `task_answer_overrides` + `task_answer_override_logs`,
`curated_variant_tasks`, `oge_variant_pool_tasks`, аналитика по `task_key`.
Вынесли именно потому, что `TaskDataService::saveTopicData()` перезаписывает
файл темы целиком — это гонки при параллельном редактировании и ноль истории.
Осталось само содержимое.

**Ссылка на задачу — это её позиция в файле.** Формат ключа:

```
topic_(\d{2})_block_(\d+)_zadanie_(\d+)_(task|statement)_(\d+)
```

Переставили задачу внутри задания — поехали ссылки в пулах вариантов, ДЗ,
уроках и аналитике. В БД это обычный внешний ключ на неизменный `id`.

**Чтение — файлом целиком.** `getTopicData()` кладёт в кэш весь JSON темы.
`topic_13.json` — 841 КБ, `topic_17.json` — 567 КБ. Чтобы показать одну задачу,
разворачивается вся тема. После добавления 3884 заданий ФИПИ с инлайновыми SVG
это станет 1.5 МБ на тему.

**Сверка с ФИПИ.** `check_updates.py` находит новые и пропавшие задания банка по
`guid`. Чтобы это работало на проде, у задачи нужен стабильный `fipi_guid` и
возможность спросить «каких guid у нас ещё нет» — в JSON это полный перебор всех
файлов, в БД один индекс.

## Что теряем и чем компенсируем

Уходя из JSON, теряем git-diff контента: сейчас правку задания видно в PR.
Компенсация — команда `tasks:export`, которая пишет те же `topic_NN.json` из
базы. Она уже есть в зачаточном виде (`ExportTasksToJson`). Тогда база —
источник истины для рантайма, а файлы в репозитории — ревьюируемый слепок.

## Схема

Две таблицы вместо одной: интерфейс рендерит **задание** (`zadanie`) со списком
задач внутри, и `zadanie.blade.php` получает именно такую структуру. Плоская
таблица заставила бы дублировать инструкцию у каждой задачи и переписывать вьюхи.

### `task_groups` — блок + задание

| колонка | тип | зачем |
|---|---|---|
| `id` | bigint PK | |
| `bank` | varchar(8) | `oge` `ege` `vpr` `alg` `geom` — направления не пересекаются |
| `grade` | tinyint NULL | 5–8 для ВПР и алгебры; NULL для ОГЭ/ЕГЭ |
| `topic` | varchar(4) | `01`…`25`, строкой — ведущий ноль значащий |
| `block_number` | smallint | |
| `block_title` | varchar(190) NULL | |
| `zadanie_number` | smallint | |
| `instruction` | text NULL | |
| `type` | varchar(40) | один из 41 |
| `svg_type` | varchar(40) NULL | |
| `payload` | json | `options`, `geometry`, `options_render_mode`, `points`, `illustration` |
| `status` | varchar(16) | `production` / `draft` |
| `source` | varchar(24) | `palomatika` / `fipi` / `palomatika_legacy` |
| `position` | smallint | кураторский порядок |

Индексы: `(bank, grade, topic, position)`, `(bank, topic, status)`, `(source)`.

### `tasks` — сама задача

| колонка | тип | зачем |
|---|---|---|
| `id` | bigint PK | |
| `task_group_id` | bigint FK → `task_groups` | |
| `position` | smallint | порядок внутри задания |
| `type` | varchar(40) NULL | переопределение типа группы |
| `payload` | json | `text`/`expression`/`options`/`svg`/`params`/`statements`/`graph_options` |
| `answer` | text NULL | |
| `answer_src` | varchar(16) NULL | `pal` `calc` `gpt` `geo` `px` `graph` `set` `tex` `manual` |
| `status` | varchar(16) | |
| `source` | varchar(24) | |
| `fipi_guid` | char(32) NULL | сверка с банком ФИПИ |
| `legacy_task_key` | varchar(160) NULL | старый ключ-позиция |
| `svg_model` | json NULL | данные, из которых нарисован SVG |

Индексы: `(task_group_id, position)`, unique `fipi_guid`, unique
`legacy_task_key`, `(source, status)`.

### Почему `payload` — JSON, а не колонки

41 тип задания несёт разные поля: у координатной прямой `point_value`,
`axis_min`, `axis_max`, `point_anchor`; у геометрии `geometry` и `params`;
у соответствия `options` и `formulas`; у темы 13 `graph_options`. Плоская схема
дала бы сорок с лишним почти всегда пустых колонок. JSON-колонка честнее: то,
что общее для всех и по чему мы ищем (банк, тема, тип, статус, ответ, guid), —
обычные колонки с индексами; то, что зависит от типа, — внутри `payload`.

### `svg_model` — отдельно и намеренно

Наши SVG тем 15–18 переносятся статикой: рендерер Паломатики рисует
концептуальную схему, а мы 890 фигур сняли с оригиналов ФИПИ попиксельно, и
перевод в параметрику ухудшил бы соответствие. Но данные, из которых картинка
получена, у нас есть (`out/topic18_model_cache/`, обмеры `geo_measure.py`), и
выбрасывать их нельзя: без них нельзя ни перекрасить под новую тему, ни изменить
размер, ни включить рандомизацию — придётся заново мерить растры ФИПИ.
Хранение стоит ноль, а право передумать сохраняет.

## Совместимость: чтобы ничего не отвалилось

`TaskDataService` остаётся фасадом — он уже единственная точка чтения банка,
меняется только его нутро. Вызывающий код (контроллеры, вьюхи, генератор
вариантов, picker) не трогаем.

Восемь таблиц ссылаются на задачу строкой `task_key`: `homework_tasks`,
`curated_variant_tasks`, `oge_variant_pool_tasks`, `task_statuses`,
`task_answer_overrides` (+логи), `oge_attempt_task_details`,
`student_topic_mastery`, `lesson_session_tasks`, плюс аналитика. Их не трогаем:
`tasks.legacy_task_key` хранит прежний ключ, и старые ссылки резолвятся. Новые
пишутся по `task_id`.

## Отключение старого банка ОГЭ

По решению Стаса старый банк (2624 задачи) не удаляется, а помечается
`source = 'palomatika_legacy'` и убирается из выдачи.

Опасение, что старое ДЗ «молча покажет другую задачу», проверено по проду и
**не подтвердилось**: домашки (`homework_topic_tasks`, 13 строк) и уроки
(`lesson_session_tasks`, 131) хранят снапшот — `task_payload` вместе с
`correct_answer`, а не ссылку. Ответы учеников (`oge_attempt_answers`, 2359)
привязаны к номеру задания в попытке. История попыток
(`oge_attempt_task_details`, 3310) хранит `task_fingerprint`, заполненный у всех
строк, поэтому подмену содержимого она покажет, а не проглотит.

Три таблицы завязаны на позицию в старом банке, и все три по решению Стаса
больше не нужны — это способ работы со старой базой:

| таблица | строк | почему не нужна |
|---|---|---|
| `oge_variant_pool_tasks` | 1110 | варианты генерируются заново при каждом старте (на проде с 2026-07-22); пул перестали наполнять 2026-07-08, а варианты создавались до 26-го |
| `task_statuses` | 2599 | деление `production`/`draft` было нужно для кураторской работы со старым банком |
| `task_answer_overrides` | 5 | ручные правки ответов старого банка |

`tasks.legacy_task_key` всё равно нужен — по нему резолвится история попыток.

## Порядок работ

1. Миграции: `task_groups`, `tasks`.
2. Команда `tasks:import-json` — перенос текущих 8377 задач из JSON в БД
   с проставлением `legacy_task_key`.
3. `TaskDataService` читает из БД, отдаёт ту же структуру. Тесты банка зелёные.
4. `tasks:export` — обратная выгрузка в `topic_NN.json` для ревью в git.
5. Пометка старого ОГЭ-банка `palomatika_legacy` и скрытие из выдачи.
6. Импорт банка ФИПИ (`fipi-sync/out/export/bank_katex.json`) отдельной командой.

## Что нужно учесть при импорте ФИПИ

* Ограничения по варианту ответа: в PWA
  `optionAnswerValue()` отдаёт `opt.id`, а при его отсутствии — порядковый
  номер. Наши ответы — номера, значит варианты ФИПИ импортируются **без**
  буквенных `id`, иначе ученик отправит `b`, а эталон будет `2`.
* Тема 24 (60 доказательств) — без ответов; решить, импортировать ли их как
  задания без автопроверки.
